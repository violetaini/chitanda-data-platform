# 节点自动采集与维护

更新时间：2026-10-18

TLS 信息来自节点程序，通过已有鉴权心跳自动进入面板，采样无需手工维护 UI。控制端预期配置与节点实际观测分别保留：系统设置集中显示证书观测，SNI 在隧道中管理；节点卡片只展示身份、状态和资源，业务域名及自动解析状态在各隧道中展示。

## 数据来源

| 字段 | 实际来源 |
| --- | --- |
| 服务端证书 SAN、颁发者、有效期、SHA-256 指纹 | 节点当前内存中实际供 TLS 服务使用的 X.509 证书 |
| 对端证书、SNI、TLS 版本、ALPN、加密套件、握手时间 | 实际 H2 / H3 物理会话完成握手后的 ConnectionState |
| HTTPS 业务入口证书 | 整合入口实际加载的公共证书；单独列为 HTTPS 入口 |
| TLS 最低版本 | 实际服务端 tls.Config.MinVersion |
| 内存、运行时长 | 节点进程 RSS 与启动时间，不是整台服务器资源 |
| 节点程序版本、支持协议 | 节点程序心跳上报的实际版本与运行能力 |
| 控制端版本 | 控制端运行目录 package.json，页面从 API 读取 |

原固定上游 SDK 没有暴露 TLS 观测回调；`patches/chitanda-tls-observer.patch` 为初始与动态扩容的 H2 / H3 会话加入观察入口，构建时校验并自动应用。回调在握手完成后采集，不改变证书验证、SNI 或加密配置，也不产生额外探测会话。升级上游时必须重新检查补丁，不能忽略 apply 失败继续构建。

## 上报结构

心跳 `tls` 使用 schema 1，包含 `collectedAt` 与 `entries`。每条记录标记 `side=client/server`、`usage=channel/https-ingress`、线路及对端范围，证书仅含公开摘要；client 还包含握手信息。控制端限制条目数量和字符串长度，过滤私钥 / PEM / 令牌及未知字段，拒绝客户端伪报其他线路或其他节点的服务端证书。

采样与活跃状态分开：证书加载成功不等于已经发生客户端验证，历史握手成功也不等于当前线路在线。离线、配置未确认、链路断开时页面明确标记状态。尚未升级或尚未握手的节点显示待上报，不填入固定域名、固定有效期或固定“验证通过”。

## 日后维护

1. 在中台管理节点及线路配置；节点后续心跳接收配置并自动更新所用线路。
2. 工作区证书由控制端按原机制签发和下发。节点实际加载新证书后更新服务端采样；接入端新的真实握手更新对端采样，复用中的旧会话显示最近一次握手信息。
3. HTTPS 入口证书若由文件加载，外部续期程序还需按该服务既有机制重载；面板将持续显示实际已加载版本，不能把磁盘上新证书当成进程已生效。
4. 保留各节点配置、账号和 CA，使用新二进制原位升级；节点身份与 credentialVersion 不变。控制端升级期间已配置业务可用私有缓存继续运行，节点服务重启时现有会话可能短暂重建。

验证：`npm test`、`node scripts/tunnel-control-node-cards-smoke.cjs`；上游补丁应用后运行 `go test -mod=mod ./pkg/client ./cmd/chitanda-transit`。真实 H2 / H3 与证书轮换集成测试在 Linux 运行，覆盖自定义 SNI、错误 SNI 不产生成功观测及完整数据回传。
